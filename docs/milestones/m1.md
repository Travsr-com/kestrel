# M1: one agent, end to end

M1 runs one coding agent headless in a gVisor sandbox, with its model calls metered and budgeted.
This page says what is proven, how to rerun the proof, and the numbers it produced.

## What M1 proves

Five scenarios run against real Docker and gVisor in CI (the `e2e` job). All five pass.

| # | Scenario | What it shows |
| :--- | :--- | :--- |
| 1 | A run completes and edits its workspace | The agent runs in a sandbox, its file edit lands in its own git workspace, and spend equals the model's token usage times the configured prices, to the micro-dollar (6,465 micro-USD for the test call). Each call also appears in the run's event stream. |
| 2 | Budget suspend survives a hard kill | A run that hits its budget is suspended and its sandbox is stopped. After `kill -9` of `kestrel serve` and a restart, the run is still suspended. Raising the budget and resuming it finishes the run. |
| 3 | The sandbox cannot reach other hosts | From inside the sandbox, a DNS name and a raw IP address both fail with a network error. The gateway is the only way out. |
| 4 | No real API key in the sandbox | The key the agent sees is a placeholder. The real key stays in the gateway. |
| 5 | Live watch | `kestrel watch` started mid-run prints every event from the first one and follows the run to the end. |

How the pieces fit:

```text
kestrel run ──► SQLite store ◄── kestrel serve (engine + gateway)
                                     │                │
                                     ▼                ▼
                          gVisor sandbox ──► bridge container ──► gateway ──► provider
                          (no other network)   (kestrel-gateway)
```

The sandbox sits on an isolated Docker network. A small `kestrel-gateway` container joins that
network and forwards to the gateway on the host. Agents reach it by IP address, because Docker's
name lookup does not work inside gVisor.

## How to run the e2e suite

You need Linux with Docker and gVisor registered as a Docker runtime (see the
[quickstart](../quickstart.md)). Then, from the repository root:

```sh
docker pull alpine:3.20
docker pull alpine/socat:1.8.0.3@sha256:beb4a68d9e4fe6b0f21ea774a0fde6c31f580dde6368939ed70100c5385b015e
docker build -t kestrel-echo-agent:test tests/e2e/echo-agent
cargo build -p kestrel-cli
KESTREL_BIN="$PWD/target/debug/kestrel" \
  cargo test -p kestrel-e2e --features e2e -- --test-threads=1 --nocapture
```

The test agent is a small script that behaves like Claude Code in headless mode. The model provider
is a mock on the host that returns fixed token counts, so no API key or money is involved.
The suite is off by default, so a normal `cargo test` never needs Docker.

## Results

Measured by the `e2e` CI job on a GitHub-hosted Ubuntu runner. These are single runs, so read them as
rough size, not as benchmarks.

### Cold start

A sandbox went from `Provisioning` to `Running` in **77 ms**. The image was already on the machine, so
this does not include pulling an image.

### Gateway latency

One model call through the gateway took **1 ms** of gateway time. The mock provider was on the same
machine and answered at once, so this shows the gateway's own overhead only. Real latency is
dominated by the provider.

## What M1 does not do yet

* Agents cannot run `git` inside the sandbox ([#22](https://github.com/Travsr-com/kestrel/issues/22)).
* Sandboxes share one internal network ([#10](https://github.com/Travsr-com/kestrel/issues/10)).
* The bridge needs hardening ([#29](https://github.com/Travsr-com/kestrel/issues/29)).
* Non-root agent images may not be able to write the workspace
  ([#24](https://github.com/Travsr-com/kestrel/issues/24)).
* The Apple `container` driver is not verified on a real Mac
  ([#11](https://github.com/Travsr-com/kestrel/issues/11)).
