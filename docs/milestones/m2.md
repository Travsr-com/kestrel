# M2: parallel and spawn, plus the UI

M2 lets one run spawn child runs, each in its own sandbox and git clone, with narrower rights and a
budget carved out of its parent's, and shows the whole tree live in the web UI. This page says what
the acceptance suite proves, how to rerun it, and the numbers it produced.

**Status: accepted.** All 14 scenarios of this suite pass in the `e2e-m2` CI job
([run 44978012451](https://github.com/Travsr-com/kestrel/actions/runs/44978012451)).

## What M2 proves

The 14 scenarios of [#45](https://github.com/Travsr-com/kestrel/issues/45) run against real Docker
and gVisor in CI.

| # | Scenario | What it shows | Test |
| :--- | :--- | :--- | :--- |
| 1 | Fan-out | A parent spawns 6 children and joins. Each child completes in its own clone on `kestrel/run-<id>`, with one commit and a clean `git status`. Each branch comes home on its own. The source repo keeps its branch and files. | `m2_s01_fan_out_to_six_children_in_their_own_clones` |
| 2 | Conflict-free by construction | All 6 children edit the same file. Every branch holds its own version, one commit on top of `main`, and nothing conflicts. | `m2_s02_same_file_edits_never_conflict` |
| 3 | A child cannot use a tool its parent lacks | The child's grant drops the tools its parent does not hold. `tools/list` does not show them, and a direct call is refused with `not permitted` and recorded on the child. The same child's call of `kestrel.join`, which it holds, succeeds. | `m2_s03_child_cannot_use_a_tool_its_parent_lacks` |
| 4 | A child cannot reach a host its parent lacks | The child's grant drops `evil.example`. From its sandbox, every host but the gateway fails, granted or not. | `m2_s04_child_cannot_reach_a_host_its_parent_lacks` |
| 5 | A child gets no secret its parent lacks | The child's grant and its signed token lack `aws_key`; a token check for it is denied. | `m2_s05_child_gets_no_secret_its_parent_lacks` |
| 6 | No escalation | A spawn with more budget than the child has is refused. A spawn asking for more depth than the child has left gets what is left; the spawn answer carries `depth` and `note`, and each lowered run records an `agent_log` line (#94, see below). A grandchild at `max_depth` 0 cannot spawn. `/kestrel` holds the run's own MCP URL, and the sandbox has no mounts but `/workspace`, `/kestrel` and the ones Docker adds. Each sandbox holds its own run token and no other: not in its environment, not anywhere under `/kestrel` or its other mounts, and not in any file or git object of its workspace. | `m2_s06_child_cannot_escalate_budget_depth_or_token` |
| 7 | Budget carving | A $1.00 root gives 6 children $0.15 each. Each tries to spend $0.30, is held to $0.15 plus at most one call, and is suspended. Every cost is tokens times price to the micro-dollar. The tree stays within $1.00 only because $0.10 of it is not carved out, and the six one-call overshoots and the parent's own call fit in that. Once each child is pinned to $0.15 plus one call, the check of the tree's total cannot fail on its own. | `m2_s07_budget_carving_holds_each_child_to_its_share` |
| 8 | No deadlock under a full cap | With a cap of 2, a parent spawns 5 children and joins. All 5 finish within 60 s, at most 2 children run at once, and the parent holds no slot while it waits. | `m2_s08_full_cap_does_not_deadlock` |
| 9 | Cancel a subtree | Cancelling the root over the API cancels its children and grandchildren, and leaves no sandbox container and no run network. | `m2_s09_cancel_removes_the_whole_subtree` |
| 10 | Network scale | Every run of the fan-out gets its own `/29` network from the Kestrel pool, and all 7 are up at once. Then 20 short sandboxes start with the CI host's default Docker pools, all 20 networks are up at once, and none fails with "address pools exhausted". The test holds every run until all of them are up, so the overlap does not depend on timing. 20 networks also fit Docker's default pools (about 30), so the proof of Kestrel's subnet plan is that every run's network is a `/29` from `10.200.0.0/16`. | `m2_s10_each_run_gets_its_own_network_and_twenty_start` |
| 11 | Travsr | A child writes and commits a file that uses a symbol, then asks Travsr (`search_symbol`) where the symbol is. The answer comes from Kestrel's private copy of the child's starting commit: it names the source repo's file and not the child's new one. Travsr ran in that copy, under the data dir, never in the child's clone; each run was indexed in its own copy; the `repo` argument the child sent never reached Travsr; and both copies are deleted once the runs end. | `m2_s11_travsr_answers_from_the_run_s_own_copy` |
| 12 | Live UI | In headless Chromium, the Run view shows the tree grow (a child shows as running before the last one exists), every status turns `Completed` without a reload, every child's stream shows its model call, the budget bar matches the API, and Fleet and Approvals load without console errors. | `ui_s12_s13_live_tree_and_approval_in_a_browser`, Playwright `s12-live-tree.spec.ts` |
| 13 | Approval in the UI | A child asks a question. The test types an answer on the Approvals page and sends it, and the child goes on with that text. | `ui_s12_s13_live_tree_and_approval_in_a_browser`, Playwright `s13-approval.spec.ts` |
| 14 | Restart in the middle | `kill -9` of `kestrel serve` while the parent waits in its join. After the restart serve resumes every run by itself. The parent spawns its six children again and gets the same six back, the children finish, the join reports each once, and every model call is counted once. | `m2_s14_restart_mid_join_resumes_and_counts_once` |

How the pieces fit:

```text
kestrel run ──► SQLite store ◄── kestrel up (engine + gateway + API and UI)
                                   │            │                 ▲
                                   ▼            ▼                 │
          parent sandbox ── kestrel.spawn ──► gateway /r/<token>/mcp   Playwright (Chromium)
          child sandboxes ── model calls ───► gateway ──► mock provider
          (each on its own network, each in its own git clone)
```

### The test agent

The agent is the M1 echo agent (`tests/e2e/echo-agent/claude.sh`), a shell script that behaves like
Claude Code in headless mode. Words in its input tell it what to do:

* A parent with `fanout=6` spawns 6 children through the Kestrel server in its `--mcp-config`
  file, then joins them. `c.WORD` is passed on to each child as `WORD`.
* A child makes one model call, then does what its words say: `commit=1` (one commit in its
  clone), `spend=N` (keep calling the model), `nap=N`, `hold=N` (wait until the test writes a
  `go` file into its workspace), `tools=1`, `hosts=1`, `escalate=1`, `ask=1`, `dump=1`,
  `travsr=SYMBOL` (commit a file that uses the symbol, then ask Travsr where it is).

Scenario 11 turns Travsr on with a fake: a shell script on the host that indexes nothing and
answers `search_symbol` by searching the files of the copy it serves. It logs where it ran and
every request it got, so the test sees exactly what reached Travsr.

The model provider is a mock on the host that returns fixed token counts, so no API key or money is
involved. Agent specs for spawned children go in `agents/` next to the database.

## How to run the M2 suites

You need what M1 needs (Linux, Docker, gVisor as a Docker runtime, see [m1.md](m1.md)), plus Node
(the version in `ui/.nvmrc`) for the UI build and the browser suite. From the repository root:

```sh
docker pull alpine:3.20
docker pull alpine/socat:1.8.0.3@sha256:beb4a68d9e4fe6b0f21ea774a0fde6c31f580dde6368939ed70100c5385b015e
docker build -t kestrel-echo-agent:test tests/e2e/echo-agent
(cd ui && npm ci && npm run build)
cargo build -p kestrel-cli
export KESTREL_BIN="$PWD/target/debug/kestrel"
cargo test -p kestrel-e2e --features e2e --test m2 -- --test-threads=1 --nocapture
```

The browser suite also needs Playwright and Chromium:

```sh
(cd tests/e2e/ui && npm ci && npx playwright install --with-deps chromium)
cargo test -p kestrel-e2e --features e2e --test ui -- --test-threads=1 --nocapture
```

`tests/ui.rs` starts `kestrel up` and the runs, then runs `npx playwright test` in `tests/e2e/ui`
with the server URL, the API token and the run ids in `KESTREL_*` variables. On a failure the
trace and screenshots are in `tests/e2e/ui/test-results`; CI uploads them as the
`playwright-test-results` artifact.

## How to read some scenarios

* **Scenario 3** calls `kestrel.ask_human` directly, as the tool the child asked for and did not
  get. Travsr is off in that test. The dropped `travsr.get_callers` is checked in the child's grant
  and in its `--allowedTools`.
* **Scenario 11** reads the issue's "the answer comes from its own clone" as "from the run's own
  code". Travsr runs on the host, so Kestrel never lets it read a workspace the agent can rewrite
  ([travsr.md](../travsr.md), Security model). It indexes a private copy of the run's starting
  commit instead. So the test checks the opposite of the issue's example: the file the child just
  wrote is not in the answer.
* **Scenario 4.** The proof that the child does not get `evil.example` is its grant, which drops the
  host. `evil.example` never resolves anywhere (`.example` is a reserved domain), so its failed probe
  proves nothing on its own. The probes of `1.1.1.1` (no DNS needed) and `api.github.com` (a granted
  host) would answer on an open network, so their failure shows the sandbox's network is closed.
* **Scenario 6.** A spawn that asks for more `max_depth` than its parent has left is not refused.
  The child gets the depth that is left. Here both ask for 5: the child gets 1, the grandchild 0.
  The lowering is reported (#94): the spawn answer carries `depth` (what the run got) and a `note`
  such as `max_depth lowered from 5 to 1 (the most this parent can give)`, and each lowered run
  records an `agent_log` line saying the same. Budget is different: a spawn that asks for more
  than the parent has left is refused.
* **Scenario 8.** A parent in its join keeps its sandbox running (it is inside a tool call) but
  gives its slot back. So up to the cap plus the waiting parent run at once. The cap counts the
  runs that hold a slot, and the suite checks that from `docker ps` samples and from the event log.
* **Scenario 14.** The suite runs no `kestrel resume` (#92). The restart suspends every run it cut
  off with `engine restarted`, and serve resumes each of them by itself (architecture section 3.3,
  "After a restart"). The parent's agent starts again from its input and spawns all six children
  again, as a real agent would: the echo agent keeps no record of them. Each spawn answers with the
  child the parent already has (`"existing": true`), so the tree still has six children and none
  counts against `max_children` twice. The suite checks each run's events for the suspension and the
  resume, the six repeated answers, a join answer with each child once, and two model calls per run
  (one before the restart, one after).
* **Scenarios 1 and 2** bring each branch home with `fetch_back`, as M1 scenario 6 does.
  Kestrel does not do that on its own yet.
* **Clean clones.** The echo agent keeps its own report files (`env.txt`, `*.out`) out of git, so a
  clean `git status` means the child's work is all committed.

## What M2 does not do yet

* Secrets are not injected into sandboxes. Scenario 5 checks the grant and the token, not a live
  secret. Injection is M3 work.
* Network grants are recorded but not enforced by an egress proxy: a sandbox reaches only the
  gateway, whatever hosts it was granted.
* A run can go over its budget by the calls it has in flight (one for an agent that calls one at a
  time, as in scenario 7), and a tree over its root budget by the sum of those overshoots. The
  gateway checks the limit before each call (architecture section 3.3), so a call that starts under
  the limit goes through even if it crosses it. In scenario 7 each child ends at 155,160 micro-USD,
  one call past its $0.15.
* A resumed agent starts again from its input; Kestrel cannot resume an agent process in the middle
  of its work. Spawns are matched by agent and input (#92), so a parent that rewords a child's input
  when it starts again gets a new child.
* The model provider is a mock, so the suite proves metering and budgets, not model behaviour.
* Travsr does not see an agent's own edits: it answers about the run's starting commit. Scenario 11
  runs a fake Travsr, so it proves where Travsr runs and what reaches it, not the real index.
* At most `gateway.max_waiting_calls` long tool calls (default 256) are held open at once across
  all runs, and the bridge is sized at 2 connections for each plus 4 per concurrent run (architecture
  section 3.3, [#80](https://github.com/Travsr-com/kestrel/issues/80)). This suite stays well
  under that; the sandbox integration suite holds 40 connections through a real bridge.
